# HTTP-сервис `employees` (1С:ЗУП, публикация `Holding_ZUP`)

Сервис возвращает учётные данные сотрудника по ФИО: организацию, подразделение,
табельный номер и должность. Предназначен для внешних систем, которым нужно
получить эти сведения из ЗУП по имени человека (справочная синхронизация,
заполнение профиля во внутреннем портале, проверка места работы).

Документ описывает поведение, наблюдаемое на текущей публикации. Пункты, которые
не подтверждены обращением к сервису, помечены как **требует уточнения** — их
нужно проверить у владельца сервиса или по коду обработчика перед тем, как
опираться на них в интеграции.

## Точка входа

```
GET http://10.12.15.112/Holding_ZUP/hs/employees
```

Адрес складывается по обычной схеме публикации 1С на веб-сервере:

| Часть | Значение | Смысл |
| --- | --- | --- |
| `10.12.15.112` | хост | Веб-сервер с опубликованной информационной базой (Microsoft-IIS/8.5) |
| `Holding_ZUP` | имя публикации | Виртуальный каталог IIS, в котором опубликована база ЗУП |
| `hs` | признак HTTP-сервиса | Фиксированный разделитель платформы для HTTP-сервисов (в отличие от `ws` для SOAP) |
| `employees` | корневой URL сервиса | Свойство «Корневой URL» объекта метаданных HTTP-сервис |

Публикация работает по HTTP без TLS. См. раздел «Безопасность».

## Аутентификация

Базовая аутентификация HTTP (RFC 7617) поверх пользователя информационной базы:

```
Authorization: Basic <base64(логин:пароль)>
```

Без заголовка или с неверными данными сервер отвечает `401 Unauthorized` и
предлагает схему Basic:

```
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="1C:Enterprise 8.3"
```

Значение заголовка — это строка `логин:пароль`, закодированная в Base64. Например
для `svc_portal_api` с паролем `P@ssw0rd`:

```
Authorization: Basic c3ZjX3BvcnRhbF9hcGk6UEBzc3cwcmQ=
```

Base64 — это не шифрование, а обратимое кодирование: логин и пароль из заголовка
восстанавливаются любым, кто видит трафик или логи прокси.

Логин служебного пользователя следует задавать только латиницей: в Basic
логин и пароль склеиваются через `:` и кодируются целиком, поэтому кириллица в
логине приводит к расхождению кодировок между клиентом и сервером и к
немотивированным `401`, а двоеточие в логине ломает разбор заголовка.

## Параметры запроса

Фильтр по ФИО задаётся тремя параметрами строки запроса:

| Параметр | Соответствие в примере | Часть ФИО |
| --- | --- | --- |
| `name1` | `Денис` | Имя |
| `name2` | `Шимонов` | Фамилия |
| `name3` | `Викторович` | Отчество |

Обратите внимание на порядок: `name1` — это **имя**, а фамилия передаётся в
`name2`. Нумерация не совпадает с привычным порядком «Фамилия Имя Отчество»,
это частый источник ошибок на стороне клиента.

**Требует уточнения:** обязательность параметров (можно ли искать только по
фамилии), чувствительность к регистру, режим сравнения (точное совпадение или
поиск по началу строки) и поведение при нескольких сотрудниках с одинаковым ФИО.

### Кодирование кириллицы

Значения параметров содержат кириллицу, поэтому в URL их нужно передавать в
процентном кодировании UTF-8. Запрос из примера в полностью закодированном виде:

```
GET /Holding_ZUP/hs/employees?name1=%D0%94%D0%B5%D0%BD%D0%B8%D1%81&name2=%D0%A8%D0%B8%D0%BC%D0%BE%D0%BD%D0%BE%D0%B2&name3=%D0%92%D0%B8%D0%BA%D1%82%D0%BE%D1%80%D0%BE%D0%B2%D0%B8%D1%87 HTTP/1.1
Host: 10.12.15.112
Authorization: Basic <base64>
```

Браузеры и большинство HTTP-клиентов кодируют такие символы сами, поэтому в
адресной строке допустимо писать `?name1=Денис`. Но при сборке URL строками в
коде кодирование нужно выполнять явно: в 1С — `КодироватьСтроку(Значение,
СпособКодированияСтроки.КодировкаURL)`, в Python — `urllib.parse.quote`, иначе
запрос уйдёт в кодировке по умолчанию клиента и фильтр не сработает.

## Ответ

Тело ответа — JSON-массив объектов. Массив используется даже для одного
сотрудника, поэтому клиент должен всегда разбирать результат как коллекцию, а не
как одиночный объект.

```json
[
  {
    "organization": "ООО \"ЛибретикГрупп\"",
    "division": "Отдел информационных технологий",
    "number": "0600-00375",
    "job": "инженер-программист",
    "name1": "Денис",
    "name2": "Шимонов",
    "name3": "Викторович"
  }
]
```

| Поле | Тип | Описание |
| --- | --- | --- |
| `organization` | строка | Организация-работодатель. Кавычки в наименовании экранированы по правилам JSON (`\"`) |
| `division` | строка | Подразделение по кадровым данным |
| `number` | строка | Табельный номер. Именно строка, а не число: значение содержит дефис и ведущие нули (`0600-00375`), при разборе как числа данные будут потеряны |
| `job` | строка | Должность |
| `name1` | строка | Имя (эхо параметра запроса) |
| `name2` | строка | Фамилия (эхо параметра запроса) |
| `name3` | строка | Отчество (эхо параметра запроса) |

Поля `name1`–`name3` дублируют переданный фильтр и полезны для сопоставления
элементов ответа с запросом при пакетной обработке.

**Требует уточнения:** возвращается ли пустой массив `[]` или ошибка, если
сотрудник не найден; попадают ли в выборку уволенные сотрудники и совместители
(у сотрудника может быть несколько кадровых назначений, и тогда логично ожидать
несколько элементов массива на одного человека).

### Заголовки ответа

```
Server: Microsoft-IIS/8.5
Content-Type: text/html; charset=utf-8
```

Тип содержимого объявлен как `text/html`, хотя фактически возвращается JSON. Так
ведёт себя обработчик 1С, если в ответе не задан тип содержимого явно. Из этого
следуют два практических вывода:

- Клиент не должен полагаться на `Content-Type` при выборе парсера — тело нужно
  разбирать как JSON независимо от заголовка. Строгие клиенты и обёртки,
  проверяющие тип (например, `response.json()` в некоторых библиотеках или
  автоматическая десериализация в типизированных клиентах), на таком ответе
  падают.
- На стороне сервиса это стоит исправить: в обработчике задать
  `Ответ.Заголовки.Вставить("Content-Type", "application/json; charset=utf-8")`.
  Правка совместима с существующими клиентами, которые парсят тело
  безусловно.

### Коды состояния

| Код | Причина | Действие клиента |
| --- | --- | --- |
| `200 OK` | Запрос обработан; тело содержит массив (возможно пустой) | Разобрать JSON |
| `401 Unauthorized` | Нет заголовка `Authorization`, неверный пароль, заблокированный пользователь ИБ | Проверить учётные данные; повтор с тем же паролем не поможет |
| `403 Forbidden` | У пользователя ИБ нет права на использование этого HTTP-сервиса | Выдать роль на использование сервиса |
| `404 Not Found` | Опечатка в имени публикации или корневом URL, либо шаблон URL не совпал | Сверить адрес с разделом «Точка входа» |
| `500 Internal Server Error` | Исключение в обработчике сервиса | Смотреть журнал регистрации 1С по времени запроса |
| `503 Service Unavailable` | База недоступна: сеанс не устанавливается, заблокирована на обновление, нет свободных лицензий | Повторить с задержкой |

**Требует уточнения:** возвращает ли сервис `400 Bad Request` при отсутствующих
или пустых параметрах ФИО.

## Примеры вызова

### curl

```bash
curl -u 'svc_portal_api:P@ssw0rd' \
     -G 'http://10.12.15.112/Holding_ZUP/hs/employees' \
     --data-urlencode 'name1=Денис' \
     --data-urlencode 'name2=Шимонов' \
     --data-urlencode 'name3=Викторович'
```

`--data-urlencode` вместе с `-G` переносит параметры в строку запроса и
кодирует кириллицу — собирать URL вручную не нужно.

### 1С:Предприятие 8.3

```bsl
Функция ПолучитьДанныеСотрудника(Имя, Фамилия, Отчество)

	ПараметрыЗапроса = "?name1=" + КодироватьСтроку(Имя, СпособКодированияСтроки.КодировкаURL)
		+ "&name2=" + КодироватьСтроку(Фамилия, СпособКодированияСтроки.КодировкаURL)
		+ "&name3=" + КодироватьСтроку(Отчество, СпособКодированияСтроки.КодировкаURL);

	Соединение = Новый HTTPСоединение("10.12.15.112", 80, "svc_portal_api", "P@ssw0rd", , 30);
	Запрос = Новый HTTPЗапрос("/Holding_ZUP/hs/employees" + ПараметрыЗапроса);
	Ответ = Соединение.Получить(Запрос);

	Если Ответ.КодСостояния <> 200 Тогда
		ВызватьИсключение "Сервис employees вернул код " + Ответ.КодСостояния;
	КонецЕсли;

	Чтение = Новый ЧтениеJSON;
	Чтение.УстановитьСтроку(Ответ.ПолучитьТелоКакСтроку("UTF-8"));
	Результат = ПрочитатьJSON(Чтение);
	Чтение.Закрыть();

	Возврат Результат;

КонецФункции
```

Кодировку в `ПолучитьТелоКакСтроку` указываем явно: заголовок ответа объявляет
`text/html`, и полагаться на автоопределение кодировки здесь не стоит.
Результат — массив, обращение к первому сотруднику: `Результат[0]["number"]`.

### Python

```python
import json

import requests

response = requests.get(
    "http://10.12.15.112/Holding_ZUP/hs/employees",
    params={"name1": "Денис", "name2": "Шимонов", "name3": "Викторович"},
    auth=("svc_portal_api", "P@ssw0rd"),
    timeout=30,
)
response.raise_for_status()

# Разбираем тело как JSON вручную: сервис объявляет Content-Type: text/html
employees = json.loads(response.content.decode("utf-8"))
```

## Безопасность

Публикация доступна по HTTP без TLS, а Basic передаёт пароль в обратимом
кодировании. Внутри доверенного сегмента сети это рабочая схема, но пароль
служебного пользователя виден в трафике, в логах прокси и в истории командной
строки. Отсюда практические требования к эксплуатации:

- Пароль хранить в секрет-хранилище или в переменных окружения вызывающей
  системы, не в исходном коде и не в константах конфигурации.
- Использовать отдельного служебного пользователя ИБ под эту интеграцию
  (например `svc_<система>_api`), с ролью, дающей только право использования
  этого HTTP-сервиса и чтение нужных кадровых данных. Права администратора для
  вызова сервиса не нужны.
- Ограничить доступ к порту на уровне сети или IIS списком адресов систем-потребителей.
- Перевести публикацию на HTTPS, если сервис становится доступен за пределами
  доверенного сегмента.

Сервис отдаёт персональные данные (ФИО, место работы, должность, табельный
номер), поэтому доступ к нему и состав получателей стоит согласовывать с теми же
требованиями, что и для остальных выгрузок кадровой информации.

## Ограничения

- Пагинации и ограничения размера выборки в контракте нет: при широком фильтре
  (**требует уточнения**, возможен ли он) объём ответа ничем не ограничен.
- Сервис только читает данные; методы, кроме `GET`, не описаны.
- Признака актуальности данных в ответе нет — нельзя отличить действующее
  назначение от устаревшего, если сервис их возвращает.
